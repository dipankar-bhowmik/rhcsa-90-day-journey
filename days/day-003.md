# Day 3: Set up a project folder structure (mkdir -p, touch, cp -a, mv, rm -i, wildcards, and brace expansion like {a,b,c}).

## Ticket
As user1 on server3, create one file and one directory in the home directory, list them with their permissions/owner/group, try moving both to /var/log and to /tmp, duplicate the file with cp and rename the copy, then erase everything created for the lab.

## What I did

```bash
# --- who/where ---
whoami                                  # user1
pwd                                     # /home/user1
id                                      # uid=1001(user1) gid=1001(user1) groups=1001(user1)

# --- 1. create one file and one directory in home ---
cd                                      # back to home
pwd
touch labfile.txt
mkdir labdir

# --- 2. list them with permissions, owner, group ---
ls -l labfile.txt
ls -ld labfile.txt labdir
ls -l                                   # also see them in the directory listing

# --- 3. move both to /var/log (expected: fail) ---
ls -ld /var/log                         # drwxr-xr-x root root
mv labfile.txt /var/log/
mv labdir /var/log/
ls -l /var/log/labfile.txt              # nothing there

# --- 4. same move to /tmp (expected: succeed) ---
ls -ld /tmp                             # drwxrwxrwt root root  (sticky bit)
mv labfile.txt labdir /tmp/
ls -l /tmp/labfile.txt /tmp/labdir

# --- 5. duplicate with cp, then rename the duplicate ---
cp /tmp/labfile.txt /tmp/labfile-copy.txt
mv /tmp/labfile-copy.txt /tmp/labfile-renamed.txt
ls -l /tmp/labfile*.txt
# also, from the practice lab:
cp -a /tmp/labfile.txt /tmp/labfile-hard-attr.txt && ls -l /tmp/labfile-hard-attr.txt

# --- 6. clean up everything from this lab ---
rm /tmp/labfile.txt /tmp/labfile-renamed.txt /tmp/labfile-hard-attr.txt
rmdir /tmp/labdir
ls /tmp | grep -i lab                   # no output

# --- 7. practice lab: hidden files and cp -a ---
cd ~
mkdir newfiles oldfiles
touch newfiles/.hidden newfiles/unhidden
cd oldfiles
ls -al                                 # only . and ..
ls -al ../newfiles                     # relative path to the sibling dir

cp -a ../newfiles/ .                   # copies the dir itself -> ./newfiles
ls -a
rm -rf newfiles

cp -a ../newfiles/* .                  # NOTE: glob misses dotfiles
ls -al
cp -a ../newfiles/. .                  # this one copies .hidden too
ls -al
```

## Verification

````bash
$ ls -ld labfile.txt labdir
-rw-r--r--. 1 user1 user1  0 Nov  3 10:14 labfile.txt
drwxr-xr-x. 2 user1 user1  6 Nov  3 10:14 labdir

$ mv labfile.txt /var/log/
mv: cannot move 'labfile.txt' to '/var/log/labfile.txt': Permission denied
$ mv labdir /var/log/
mv: cannot move 'labdir' to '/var/log/labdir': Permission denied

````

Why: /var/log is drwxr-xr-x root root. I am not the owner and I am not in the owning group, so I only get r-x — no w on the directory, and write on a directory is what mv/touch/cp need to create an entry inside it.

````bash
$ ls -ld /tmp
drwxrwxrwt. 9 root root 4096 Nov  3 10:16 /tmp
$ mv labfile.txt labdir /tmp/ && echo OK
OK
$ ls -l /tmp/labfile.txt /tmp/labdir
-rw-r--r--. 1 user1 user1  0 Nov  3 10:14 /tmp/labfile.txt
drwxr-xr-x. 2 user1 user1  6 Nov  3 10:14 /tmp/labdir
````

/tmp is 1777: everyone gets rwx, so creating entries works. The trailing t is the sticky bit — it only restricts deleting/renaming other people's files, it does not stop me writing new ones.

Ownership after the move: the file was user1:user1 in home and is still user1:user1 in /tmp. Home and /tmp are on the same filesystem here, so mv was a pure rename (same inode). Cross-filesystem mv would have become copy+delete and the owner would have been rewritten to me.

````bash
$ cp /tmp/labfile.txt /tmp/labfile-copy.txt && mv /tmp/labfile-copy.txt /tmp/labfile-renamed.txt
$ ls -l /tmp/labfile*.txt
-rw-r--r--. 1 user1 user1 0 Nov  3 10:17 /tmp/labfile-renamed.txt
-rw-r--r--. 1 user1 user1 0 Nov  3 10:14 /tmp/labfile.txt
````

cp made a new inode (different from the original), and mv on the same fs just renamed it. Two separate files remain.

Hidden-file proof from the practice:

````bash
$ cp -a ../newfiles/* . ; ls -al
drwxr-xr-x. 2 user1 user1 30 Nov  3 10:31 .
drwx------. 8 user1 user1 4096 Nov  3 10:31 ..
-rw-r--r--. 1 user1 user1  0 Nov  3 10:28 unhidden      # .hidden MISSING
$ cp -a ../newfiles/. . ; ls -al
-rw-r--r--. 1 user1 user1  0 Nov  3 10:28 .hidden       # now present
-rw-r--r--. 1 user1 user1  0 Nov  3 10:28 unhidden
````

Cleanup verified: ls /tmp | grep -i lab returns nothing, rmdir /tmp/labdir exited 0.

## Break and fix
Three things I broke on purpose:

rmdir on a non-empty directory — rmdir labdir gave rmdir: failed to remove 'labdir': Directory not empty.
Correct: rmdir only removes empty dirs. Fixed with rm -r labdir (and for a throwaway /tmp dir, rm -rf).
Lesson: rmdir is the safe one; rm -rf is the one that can eat a typo'd path.

Glob misses dotfiles — cp -a ../newfiles/* . silently did not copy .hidden. No error, no warning — this is the dangerous kind of failure. Fixed with cp -a ../newfiles/. . (the trailing /. makes the source "the directory and its contents"), or cp -a ../newfiles/.[!.]* ../newfiles/* . if I want to be explicit.

Locked myself out of my own file — chmod 000 labfile.txt, then cat labfile.txt → Permission denied even though I own it. Fixed with chmod 640 labfile.txt (I'm the owner, so I can always chmod back; root never loses access). Learned not to test permission behaviour on the only copy of something I need.

Nothing was unrecoverable; no reboot needed.

## Runbook note

Goal: prove a normal user can write in /tmp but not in /var/log, and understand why.

1. id; pwd; ls -ld /var/log /tmp — read the mode string and owner/group before touching anything.

2. touch ~/labfile.txt; mkdir ~/labdir; ls -ld labfile.txt labdir — confirm both are user1:user1.

3. mv labfile.txt labdir /var/log/ — expect two "Permission denied". That is the correct, documented result; do not escalate.

4. mv labfile.txt labdir /tmp/ — expect success. Note the t (sticky) on /tmp.

5. cp /tmp/labfile.txt /tmp/labfile-copy.txt; mv /tmp/labfile-copy.txt /tmp/labfile-renamed.txt — duplicate, then rename the duplicate.

6. Verify: ls -l /tmp/labfile*.

7. Rollback: rm /tmp/labfile*.txt && rmdir /tmp/labdir, then ls /tmp | grep -i lab → empty. If anything landed in /var/log by mistake, you need root to remove it.

8. If a move "works" but the owner changed, check whether it crossed a filesystem (df /home /tmp) — that's copy+delete, not rename.

## What I got wrong or learned

Read the mode string from the left and match yourself to owner/group/other. /var/log failing isn't a bug, it's drwxr-xr-x root root and me being "other". I now look at ls -ld before running a command, not after it fails.

ls -l dirname lists the contents; ls -ld dirname lists the directory entry itself. I wasted a step early on trying to see a directory's own permissions.

Write permission is needed on the parent directory, not on the file, to create/rename/delete an entry. That's why I can delete a chmod 000 file I own but can't create a file in a directory I can't write.

Sticky bit on /tmp limits deletion, not creation — I'd assumed the reverse.

mv on the same filesystem is a rename (inode and owner preserved); across filesystems it's cp+rm. Worth remembering for later when a "move" silently changes ownership to the moving user.

cp -a preserves mode/owner/timestamps where allowed; plain cp doesn't. On my own files it looks identical, so I need to test it as root or cross-user to actually see the difference.

Silent failures are the scary ones. The * vs /. glob difference threw no error at all. I should default to ls -a after any bulk copy.
